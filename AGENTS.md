## OVERVIEW
SecRandom is a GPLv3 C#/.NET desktop app for fair random drawing in education scenarios. Stack: .NET solution, Avalonia + FluentAvalonia UI, Microsoft.Extensions.Hosting DI, xUnit v3 tests.

| Orchestrated draw (编排抽取) | `SecRandom.Core/Models/Orchestration/OrchestrationModels.cs`, `SecRandom.Core/Services/Orchestration/` (`OrchestrationOrdering`, `OrchestrationScheduler`, `OrchestrationStore`, `OrchestrationVerification`), `SecRandom.Core/Services/Draw/DrawModeSelection.cs`, `SecRandom/Views/SettingsPages/Picking/OrchestrationSettingsPage.axaml(.cs)`, `OrchestrationRulePageBase.axaml(.cs)`, `OrchestrationRulePages.cs`, `OrchestrationEditingSession.cs`, `SecRandom/Services/Draw/SharedDrawServices.cs`, `docs/orchestrated-draw.md` | `DrawMode.Orchestrated` is neither a page nor a repeat policy: the order is decided *before* the draw, so a round is "take the next participant" instead of sampling. It is therefore the third choice of each channel's 「抽取方式」 dropdown (随机抽取 / 公平抽取 / 编排抽取, id `DrawModeCatalog.OrchestratedOptionId = "builtin.orchestrated"`, deliberately not a registered sampling algorithm) and is gone from the 「抽取模式」 repeat dropdown. Selecting it still persists `DrawMode.Orchestrated`, because the draw side reads only that; `DrawModeSelection.SelectOrchestrated` first records the channel's previous repeat policy in `OverridableDrawSettings.SampledDrawMode`, and `LeaveOrchestrated` restores it when the user picks a sampling method again — without that, one spell of orchestration would silently flatten a 半重复 setting to 不重复. While orchestrated the channel pages keep the 抽取模式 card visible — its three-item dropdown is bound to `SampledDrawMode` (the remembered repeat policy, always a valid 0..2 index) rather than to the four-valued `DrawMode`, so picking 编排抽取 can never push `SelectedIndex` to an out-of-range 3 and blank the selection — and hide only the 公平抽取策略 card; `S_DrawMode`/`S_FairDrawMode` keep their x:Names for settings search. An 编排名单 is its own entity (`OrchestrationProfile`, `data/config/orchestration.sro` plus legacy JSON migration, `FormatVersion = 2`) bound to one `(target, source list)` pair, keyed by roster `RecordId`; only one list per pair is active, and a missing source record is flagged `IsSourceMissing` instead of deleted. The profile is edited as **five separate lists**, not one mixed grid: 「排斥」is global (`OrchestrationMember.IsExcluded`), while 「权重」/「延后」/「顺序」/「必中」 are per round (`OrchestrationRound.Weights`/`Skipped`/`Order`/`Guaranteed`, sparse, up to 10 rounds). `OrchestrationProfile.Rules` holds one switch per list and is the only place the lists can be muted: a list switched off keeps its data but stops participating, and 「顺序」and 「必中」are **mutually exclusive switches** (`SetEnabled` turns the other off) because both answer "who goes first" — with both populated in a hand-edited file, 必中 wins and the queue only seats the remainder, so nobody is seated twice. Ordering is a **queue**, not a set of absolute slots: `OrchestrationOrdering.Resolve` drops excluded/deferred/already-drawn members, puts the guaranteed group (internally by effective weight, stable) or else the round queue in front, then fills the rest by weighted sampling without replacement (`DrawEngine.CalculateStudentWeight`, manual weight is a multiplier clamped 0–100 that never changes the zero set) and finally the zero-weight tail by draw count descending, so nobody is ever dropped from a round. Because every draw re-resolves with the round's already-drawn members, a member queued third really comes out third after the first two leave, instead of being re-seated third inside the shrinking remainder. The old absolute-position `Pins` list survives only as a migration input: `OrchestrationStore.Normalize` (called on load and save) folds its positions into `Order` in pin order and then drops the field; it also clamps `RoundCount`, fills missing lists, and filters ids whose member is gone. The settings page is an **overview**, not an editor: command bar (当前名单 drawer / 新建 / 同步 / 名单设置 / 启用·停用), round row, channel-status strip, five `FASettingsExpander` cards that only carry a one-line summary each plus a 设置 button, and a separate `FASettingsExpander` of five `ToggleSwitch` rows for the rule switches. Each card jumps to its own **hidden** sub-page (`settings.picking.orchestration.{exclude,weight,defer,order,guarantee}`, `isHide: true`, never in the sidebar or settings search), and the five sub-pages share `OrchestrationRulePageBase` (`OrchestrationRulePages.cs` declares the five `[PageInfo]` classes): header + round picker + rule hint + search/count toolbar + a member list whose rows are toggles, a weight box, or position numbers with up/down buttons — so a member's 排斥/延后/权重/位置 is edited in exactly one place and `OrchestrationMemberDrawer` no longer exists. The overview hands `(profileId, round)` to the sub-page through `OrchestrationEditingSession` instead of letting a hidden page guess its context, and reloads on return so a sub-page save is visible immediately. The editor drawer (`OrchestrationEditorDrawer.axaml(.cs)`) still creates/rebinds a profile and immediately imports the source roster's members. A channel-status strip names the bound channel's draw mode through the same `Effective*Settings` the draw itself reads, warns when the selected list is not active, and offers 切换为编排抽取 that goes through `DrawModeSelection.SelectOrchestrated` on `RollCallSettingsConfig`/`LotterySettingsConfig` (so the previous repeat policy is kept for when the user switches back) — a list whose channel is not orchestrated would otherwise look perfectly enabled and never be read. 随机顺序 / 复制到其他轮 / 清空名单 live on the 顺序 sub-page (clear removes only that one list), and every write goes through the profile mutators (`SetExcluded`/`SetSkipped`/`SetGuaranteed`/`SetOrder`/`SetWeight`) so the cross-list invariants hold even in a hand-edited file. Because those mutators silently dissolve a conflicting entry in another list, every click that would do so asks first: a `FAContentDialog` lists the lists (and rounds) that will be cancelled, 取消 restores the `OneWay`-bound checkbox, 随机顺序 / 复制到其他轮 warn when 必中 members would be moved out, and the overview's 顺序/必中 switches say which sibling they will close. The proof is still generated: `SequentialOrder`(4) sampling with `StudentOrchestrated`(19)/`LotteryOrchestrated`(20) commits the positions in the candidate weight slot, and the audit carries only `fairness.orchestration = {round, roundCount}` (e.g. engine v3.6.0, see `docs/proof-orchestration-protocol.md`). Roll call, quick draw, and lottery all take the same branch and advance the round when the round is exhausted or reset; with no active 编排名单 the channel falls back silently to the ordinary random draw, and the main pages expose no orchestration state. |

- Usage statistics are a third, separate channel: `PlatformUsageReportService` counts roll-call, lottery, and app-launch events through the platform-neutral `UsageMetricCounter` and posts `platform_id`/`field_key`/`delta` daily increments to the aggregate reporting entrance `https://appwrite.sectl.cn/api/stats/report` (`PlatformStatsApi.ReportUri`). The payload deliberately carries **no** time field: the service side stamps each increment with its own receive time and owns the weekly/monthly/lifetime figures, so the client's clock and timezone can never move an event into another bucket and no client-generated period string (`period`) is sent at all. The client therefore reports only the `daily_*` field keys (`daily_roll_call_count`, `daily_lottery_count`, `daily_app_launch_count`) and keeps just the current local day's counts plus the unsent increment queue in `data/config/usage-stats.json`. It is gated by `PrivacySettingsConfig.OnlineStatusMode == Off`, counts a draw only after the transactional commit succeeded, persists counters by atomic replace, restores a failed increment for the next attempt (so a partial batch is never replayed wholesale), and must stay best-effort — no statistics failure may reach a draw. The service-side counters are shared with the v2 client, which still reports its own period strings, so a server that starts deriving the coarser periods from daily rows must not do so for v2 traffic as well.
- Version usage is the fourth statistics figure: `PlatformVersionReportService` posts `platform_id`/`version`/`device_uuid` to the same aggregate reporting entrance, where the presence of `version` is what makes it a version report; the service dedups by identity and keeps one current version per identity (the sum over versions is the platform's deduplicated user count, which a last-value field report and a usage increment cannot produce). The account identity the API also accepts (`user_id`) is deliberately **never** sent: a version figure must not be tied to a SECTL account, so the lowercase `DeviceUuidStore` device UUID is the only identity and the payload carries nothing else. It is deliberately **not** gated by `OnlineStatusMode` either — the version mix is the project's own release baseline — and its payload stays minimal for that reason: the version plus that one device UUID, never an address, region, or account. It reports exactly once per process (the API asks for one report per start; no polling, no retry storm, no state), so nothing has to be re-reported when a user signs in or out. The reported version is `GlobalConstants.Version` **including its `v` prefix**, because the service groups people by that exact string (do not switch it to `Tag` or strip the prefix). The report must stay on the thread pool (`Task.Run` from `ExecuteAsync`): `Host.StartAsync` runs a hosted service synchronously up to its first incomplete await, so the device-UUID file access and the HTTP send must neither run on nor delay the startup thread; a rejected or unreachable endpoint only costs statistics.
- All SECTL statistics reporting goes through the one aggregate entrance `PlatformStatsApi.ReportUri` (`POST /api/stats/report`), never a per-type endpoint: the four old endpoints (`/api/stats/online`, `/api/stats/usage/increment`, `/api/stats/version`, `/api/fields/values`) are compatibility-only and must not be reintroduced. The service judges the report type from the payload keys and stops at the first hit — (1) `field_key` **and** `value` → field, (2) `version`/`app_version` → version, (3) `metrics`/`increments`/`usage`/`delta`/`metric_key` → usage, (4) anything else carrying `platform_id`/`device_uuid` → online — and answers `400` when nothing matches. That judgment is why the payload shapes are load-bearing rather than cosmetic: posting the right fields to the wrong old endpoint, or adding a field of an earlier rule (a `value` in an increment, a `version` in a heartbeat), does not fail, it silently books the number under another figure. Keep `PlatformStatsReportEntranceTests` matching the documented order if the API's rule ever changes.

- Security credentials must never be stored in `MainConfigModel` or `settings.json`. The sole credential file is `data/config/security/credentials.json`: its internal `FormatVersion` is authoritative, uses Argon2id-derived key material plus AES-256-GCM for portable storage, and must not depend on DPAPI, Keychain, `secret-tool`, or a versioned filename. Do not read or migrate older credential files. `SecurityCredentialStore` restricts the whole `data/config/security` directory to the current user once per process and on every save (Unix `0700` directory with `0600` files and temporary files; Windows breaks ACL inheritance and keeps only the current user plus SYSTEM and Administrators), because that directory also holds the readable `totp-standalone.json` copy; the hardening is best-effort and must never leave the directory unreadable to the app itself. Lockout state deliberately stays outside the AES-GCM authenticated data — a failed attempt happens without the encryption key, so `FailedAttempts`/`LockedUntilUtc` must remain writable through `SaveMetadata`, which also means anyone who can rewrite the credential file can reset the lockout: the lockout only restrains callers that cannot write that file.
- The security settings themselves are no longer in `settings.json`. `SecuritySettingsConfig` (protection master switch, factor selection, protected operations, Sudo, integrity check) lives in `data/config/security/settings.json` through the app-layer `SecuritySettingsStore`: an AES-256-GCM envelope (`FormatVersion`/`Nonce`/`Tag`/`Ciphertext`, authenticated with the fixed `SecRandom/SecuritySettings/v1` associated data) plus a device-local random 256-bit key in the sibling `settings.key`. `MainConfigModel` no longer declares the property; a set-only `security_settings` bridge captures the legacy plaintext block once so the first run of this build migrates it and then rewrites `settings.json` to drop it. The read rules are load-bearing: a file that exists but cannot be decrypted, or a file that is gone while a security password is configured, must **not** fall back to "protection off" — the store returns maximal protection (`SecurityEnabled` plus every `Protect*`, with the factor flags left to the credential-derived `NormalizeSettings`) and sets `IsIntegrityCompromised`, so editing or deleting the file is never a way to turn protection off. A fresh install with no credentials still writes defaults with protection off, and the legacy bridge is consumed only while the encrypted file is absent, so neither a later `settings.json` edit nor an imported archive can re-specify these switches. The device key is what makes this work without a password prompt at startup — "should this operation verify?" must be answerable before any verification happens — so it shares the credential directory's owner-only hardening instead of the password-derived key; anyone who can read that directory can forge the settings, the same boundary as rewriting `credentials.json` to reset the lockout.
- Because the protection switches left `settings.json`, `ControlSettingsCatalog` no longer describes a `security` category at all (it used to be described-but-read-only), so the control plane can neither read nor write them. The archive pre-import gate was reworked to match: `IArchivePreImportGuard.AuthorizeImport()` takes no candidate and asks the host for one fresh verification (no sudo state counts) whenever protection is active, so importing a settings file or restoring a backup stays a protected operation even though no archive can carry the switches any more. Export is deliberately not gated: automatic and cloud backups run in the background where no dialog can be raised. The whole `data/config/security` directory — now also holding the protection switches — stays excluded from every export, cloud backup, and the Android provider.
- While `SecuritySettingsConfig.RequireAllSelectedFactors` is off ("any selected method" mode) every selected factor verifies on its own, and TOTP cannot be checked without its seed, so that mode keeps a password-free seed copy in the sibling `data/config/security/totp-standalone.json` (written only while the mode is off and TOTP is configured; deleted when the mode turns on or the password is removed). The directory stays excluded from every export, cloud backup, and the Android provider, and the settings description discloses the trade-off. Never move that copy into `credentials.json`: its AES-GCM authentication data covers only `FormatVersion`, the password credential, `HasTotp`, and USB bindings, so a readable seed field there would be read before any authentication and would silently bypass the existing tamper detection.
- OmniTTS cloud speech API keys are credentials too: they live in `data/config/voice/omnitts-keys.json` via `OmniTtsCredentialStore` (app-layer, atomic replace), never in `VoiceSettingsConfig`/`settings.json`, IPC payloads, logs, telemetry, backups, or the Android DocumentsProvider. OmniTTS is voice engine 2 (`OmniTtsSpeechProvider.OmniEngine`), sits beside System SAPI (0) and Edge TTS (1), and is a unified cloud TTS engine whose providers are OpenAI, Gemini, FishAudio, MiMo, and Custom OpenAI-compatible. OpenAI, Gemini, and MiMo voice choices use documented preset sets; Gemini uses native `/v1beta/interactions` synthesis and wraps its 24 kHz PCM response as WAV. MiMo voice-design and voice-clone models use model-specific chat-completions payloads; clone references are WAV files kept privately under `data/config/voice/mimo-voice-reference.wav`, identified by a hash, and excluded from settings, archives, IPC, and logs. - Security authorization always flows through `ISecurityService`; do not add direct validation checks to tray handlers, windows, ViewModels, or linkage code. Passwords require at least 6 characters, with no artificial character-class rule. Strength feedback is advisory only: the password editor renders `PasswordStrengthEvaluator` (`SecRandom.Core/Services/Security/PasswordStrength/`, zxcvbn-style dictionary/pattern guess-count bands), and that score must never become a save gate — a rule-shaped "must contain X" meter is the same artificial constraint this section forbids.
- Sudo mode is opt-in but on by default (`SecuritySettingsConfig.SudoModeEnabled`); turning it off makes every protected operation verify again. While it is on, a successful verification skips re-verification for `SudoModeDurationSeconds` (default 20s, 10–600s in the security page). - In PowerShell release-workflow regex strings, delimit a variable immediately followed by a colon as `${variable}:`; `$variable:` is parsed as a scoped-variable reference and makes the whole script fail to parse.
- The desktop `Publish Desktop` and UIAccess publish steps must run `dotnet publish` with `-p:BuildInParallel=false -p:UseSharedCompilation=false` and must check `$LASTEXITCODE` after every publish. The two full/light publishes share the same `obj/` tree, so parallel builds and the shared `VBCSCompiler` race intermittently with `CS2012` file-lock failures on Windows; a masked (unchecked) failure leaves `publish/full` incomplete and breaks downstream portable/installer packaging with confusing "file does not exist" errors. Keep the `Verify bundled audio runtime` step enabled so an incomplete self-contained publish is caught at its source instead of silently producing broken artifacts.
- The mobile `Build Android APK` and `Publish unsigned iOS arm64 IPA` steps must also pass `-p:BuildInParallel=false -p:UseSharedCompilation=false` (and the iOS step runs with `set -euo pipefail`). The shared `SecRandom.Core`/app graph is otherwise scheduled twice in parallel within a single build, racing on `obj/Release/net10.0` resource outputs with `MSB3554`/`CS1566`/`MSB4018` "being used by another process" failures on any platform. The iOS publish is the release critical path: the Mono/LLVM AOT step is ~95% of that job, and the SDK parallelizes it only to `Environment.ProcessorCount / 2`, which is integer 1 on the 3 vCPU macOS runner; the step therefore passes `-p:AotCompileMaxDegreeOfParallelism=2` to keep two cores busy inside the runner's 7 GB. `MtouchUseLlvm` stays at the SDK's Release default (`true`) — clearing it would trade runtime code quality for build time.
- Android release signing decodes `ANDROID_SIGNING_KEYSTORE_BASE64` by trimming whitespace and translating URL-safe base64 (`-`→`+`, `_`→`/`) before `Convert.FromBase64String`, then validates the bytes with `keytool -list` before invoking `dotnet build`. Do not strip non-base64 characters blindly: a junk character (beyond whitespace/URL-safe chars) means the secret value itself is malformed, and deleting it silently corrupts the keystore so apksigner later fails with the opaque `MSB6006: "java" exited with code 2`. A decode failure must report the offending character's code point and require re-provisioning the secret, never a lossy strip. `keytool -J-*` options must be passed through array splatting (`& keytool @args`) — as bare `-J-Duser.language=en` tokens PowerShell splits them into `-J-Duser` + `.language=en`.

- Test project currently includes `UnitTest1.cs` coverage for legacy privacy/telemetry migration behavior.
- `vendors/EdgeTtsSharp/` is the Edge TTS synthesis submodule (SECTL's own repository, not a third-party mirror). The endpoint credentials belong to the submodule now: `Edge_tts_sharp/EdgeTtsGecToken.cs` mints the `Sec-MS-GEC` token, and `EdgeTts.CreateSynthesisUri()` rebuilds the address with a fresh token on every synthesis, pairing the v2 token `"<16 hex CS64>-<64 hex digest>"` with `Sec-MS-GEC-Version=2-<chromium>`. ### Verification protocol boundary

Formal notarization is a server-signed v3 branch. It accepts registered random/fair sampling specifications and commits the complete zero-seed request, algorithm specification hash, formal engine version 3.6.0, candidate pool, weights, guaranteed flags, anonymous audit, roster digest, context, lock receipt and final result. Ordinary offline random/fair proofs retain the 3.5.0 compatibility chain. `DrawMode.Orchestrated` and sequential/orchestrated profiles are rejected before submission with `formal_notarization_unsupported_for_orchestration`; ordinary offline orchestration proofs remain supported. The commitments detect changes to the proof or declared input, but do not prove the real roster was complete/authentic before submission or that the local binary is official.

The verification settings page links to the hidden `settings.general.proofPlayback` proof playback center: proofs are grouped by local date and shown in a table, locally replayed before they can be shown, and played through the existing `main.rollCall` or `main.lottery` page. Playback always uses the proof's complete result set, waits three seconds after the result animation, does not create history, and temporarily disables all application windows, restoring their prior visibility, geometry, state, topmost and enabled values when it ends. The official website action remains disabled at `https://secrandom.sectl.cn`.
