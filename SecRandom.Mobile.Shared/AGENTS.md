# SecRandom.Mobile.Shared/ AGENTS.md

## Scope

This project is the shared Android/iOS Avalonia SingleView adaptation library. It is referenced by shared `SecRandom.App`, which owns one Host and selects its mobile branch for a SingleView lifetime. This library supplies mobile routes, root chrome, media/update/status services, and platform seams only. The Android and iOS heads own platform entry points.

## Project Layout

- This library always builds as neutral `net10.0`. Its `AssemblyName`/`RootNamespace` stay `SecRandom.Mobile` so Core `InternalsVisibleTo("SecRandom.Mobile")` and `avares://SecRandom.Mobile/` resource URIs keep working; C# namespaces stay `SecRandom.Mobile.*`.
- `BuildMobile=true` is consumed only by the `SecRandom.Android` / `SecRandom.iOS` head projects: it switches each head to `net10.0-android` / `net10.0-ios` Exe output. `MobileTargetFramework` no longer exists; build the head project directly for a platform-specific build. The heads set `PlatformStartupContext` with a `MobilePlatformServiceRoot` before shared `SecRandom.App` is initialized. CI builds Android packages and continuously compiles the unsigned iOS arm64 target. The unsigned arm64 IPA is a required input to manual release publication and is uploaded with the other release assets. iOS device distribution and in-app update delivery remain deferred.
- Platform seams live behind injectable contracts in this library: `IMobileUpdateInstaller` (with `UnsupportedMobileUpdateInstaller` fallback) abstracts update package staging/installation, `IMobileMediaPlayer` (with `UnsupportedMobileMediaPlayer` fallback) abstracts native local-media/TTS playback, and `MobilePlatformServiceRoot.StartupErrorLogger` lets the Android head attach `Android.Util.Log` startup diagnostics. The shared library must not contain `#if ANDROID` / `#if IOS` platform code.
- Telemetry is compiled only by the shared `SecRandom` project. Its mobile build excludes `Sentry.Profiling`, and `SentryTelemetrySdkAdapter` skips profiling integration under `SECRANDOM_MOBILE`; `App` owns the same telemetry lifecycle for both platforms. Unhandled-exception hooks live in the platform heads' `MobileEntryPoint.cs` and report through `IAppHost.TryGetService<TelemetryRuntimeService>()`; upload is gated by `PrivacySettings.SentryTelemetryEnabled`.
- `MobileRootView` owns fixed mobile chrome, a keyed `UserControl` page outlet, and a separate modal-only `ViewHostControl` attached through `SingleViewHostProvider`. `MobileApplicationServices.AddMobileRuntimeServices()` contains mobile-only registrations and routes; keep them limited to supported mobile features.
- Before building its mobile branch, shared `App` calls `Utils.ConfigureMobileDataRoot()` once to select `LocalApplicationData/SecRandom/data`. The branch calls `AddCoreRuntimeServices()`, assigns `IAppHost.Host` only for transitional Core consumers, and clears it during shutdown. Never reuse the desktop package-root data path or add desktop hosted services.
- `MobilePlatformServiceRoot` must explicitly report unsupported desktop window, tray, shortcut, UIAccess, URL registration, and background-residency capabilities.

## UI And Resources

- The fixed bottom bar selects keyed pages: `main.rollCall`, `main.history`, `main.overview`, and `settings.mobile`. The root shell must not directly construct business pages. `MobileDrawPage`, `MobileHistoryPage`, `MobileOverviewPage`, and `MobileSettingsCatalogPage` are ordinary `UserControl` pages selected by `IMobileNavigator`; only modal independent views use the root's MVE host. Each mobile settings destination is independently registered under `settings.mobile.*`; the catalog retains exactly `通用`, `个性化`, `名单管理`, `抽取`, `备份`, `更新`, and `关于`, grouped under `偏好` / `数据` / `应用` section headers, with the `更新` entry projected by `MobileCapabilities.SupportsInAppUpdate` (hidden when the platform installer is unsupported).
- Mobile keeps the Fair/Random roll-call mode selector, but Fair must use the fixed `MobileDesktopDefaultsV1` Core policy snapshot and must not expose or consume persisted `FairDrawSettings`. Backup/restore uses Core `DataArchiveService` (already registered by `AddCoreRuntimeServices()` with the Null post-import hooks) behind the system StorageProvider pickers: exports stage a local temp file then copy its stream into the picked `IStorageFile`, imports copy the picked stream to a temp file, run the v3 manifest inspection, and only execute the import after explicit confirmation. All file exchange is stream-only — never assume shared-storage paths under Android SAF — and busy operations disable every action with progress text. Do not add desktop-only settings, tray/window controls, shortcuts, OOBE, notification surfaces, or fake inactive controls.
- `MobileRollCallService` is the mobile-only orchestration boundary for list switching, group/gender scope snapshots, multi-member draws, remaining members, and scoped temporary-record reset. It composes existing Core filtering, mobile fairness policy, draw engine, and `IDrawCommitService` without expanding `IRollCallSession` or copying desktop ViewModel/window effects. The draw page presents these operations in a phone action panel; desktop left/right panel placement is not a mobile setting.
- `MobileOnlineStatusService` is a mobile-only hosted runtime consumer of `PrivacySettings.OnlineStatusMode`: `Off` makes no network requests; `Anonymous` uses an empty UUID and no IP-derived data; `Full` uses a persisted mobile-private `data/config/device-uuid.json`. Native device types are `android` and `ios`; do not report native mobile clients as web clients.
- Mobile pages live under `Views/` as paired `.axaml`/`.cs` `UserControl` implementations. AXAML owns each page's fixed layout, page shell, and DynamicResource styling; DI-backed code-behind owns dynamic draw state, runtime DataGrid schemas, dialogs, StorageProvider flows, and transactional record mutations. Keep small view construction helpers local to their page or `MobileViewFactory`; Core services remain the reusable backend boundary.
- Mobile uses the shared application style resources and default Avalonia/Fluent control themes. Do not add a separate mobile style bundle or a mobile-specific theme layer. Dynamic application-resource bindings may be used when a shared resource exists; otherwise rely on the control default.
- Mobile uses `FluentAvaloniaTheme` and FluentAvalonia controls as its primary visual component library so settings stay aligned with the desktop app. `MobileSettingRow` wraps `FASettingsExpanderItem`; the fixed four-item `MobileNavigationBar` uses native Avalonia buttons because FluentAvalonia 3.0.2's `FAItemsRepeaterAutomationPeer` crashes during Android accessibility traversal. Avalonia-native controls also own the SingleView host, page `ScrollViewer`, and platform touch/layout boundaries. Mobile icon sources must use the mobile assembly font URI rather than Core's desktop `avares://SecRandom/` URI. Reusable mobile controls live in `Controls/`: `MobileCard`, `MobileSettingRow`, `MobileEmptyState`, and `MobileSectionHeader`; draw/list/history selectors use the default `TabStrip` theme.
- Mobile history and list management use `Avalonia.Controls.DataGrid` for real column headers, sorting/resizing, editing, and horizontal overflow at phone widths. History tables expose profile plus overview/record modes and never display internal `RecordId`; the current fair weight is only shown for the active student profile, and prize weight is shown only for Pan mode. List tables are read-only at cell level: normal fields edit through the row More dialog, while desktop-compatible `DrawImageAttachedSettings`, `DrawMusicAttachedSettings`, and `SpecificAnnouncementAttachedSettings` live in a separate attached-settings column. Every row mutation locates records by `RecordId`; settings preserve unknown `AttachedObjects` entries. Images and music import through StorageProvider streams into the private `data/images` / `data/audio/music` directories. `MobileMediaLibraryService` clears global and record-level music references before deletion, while Android/iOS heads provide actual playback/TTS through `IMobileMediaPlayer`; a media failure must never invalidate a committed draw.
- Every page-level `ScrollViewer` stretches inside the physical view host, enables vertical inertia, and disables scroll chaining. Clickable setting rows must cancel their click visual/action after pointer movement so they never consume a vertical swipe.
- Animation primitives live in `Views/MobileAnimations.cs`: page enter and result reveal use Android-safe opacity fades (250-400 ms, CircleEaseOut), plus name roll for in-progress draws and state cross-fade. Animations are interruptible per control — starting a new one cancels the old, and visual-tree detach cancels. Animation failures must remain non-fatal because they are decorative. Keep them light; do not port the desktop rolling animation.
- Settings pages should derive from `MobileSettingsPageBase` (light header, back button, scroll, enter transition). Capability projection (`IsLotteryEnabled`, `IsAndroid`, `SupportsInAppUpdate`) is consumed only through `MobileCapabilities` or the base-class pass-throughs, never via raw `OperatingSystem` checks or direct service lookups in pages.
- The shared list/pool name fallback is `MobileDefaults.ProfileName`; do not re-hardcode `"default"`.
- Mobile uses the platform system font by decision recorded in DESIGN.md; do not link the desktop MiSans payloads.
- Mobile strings live in `Langs/Mobile/`; preserve the base resx/designer registration pattern in the project file. `Resources.resx` is the Chinese base; `Resources.en-US.resx` and `Resources.ja-JP.resx` are satellite variants that must keep exact key parity with the base and must not be registered in the csproj. All page/control/service strings resolve through `Langs.Mobile.Resources` (LR); no hardcoded UI strings.
- Shared `App.Initialize()` reads startup settings before Host construction and applies both shared and mobile resource cultures. Language switching is restart-free: the general settings page writes the config, applies the mobile culture, then uses `IMobileRootViewReloader` to close/destroy the current root-view host session, detach it from `SingleViewHostProvider`, swap in a fresh `MobileRootView`, and re-show the default `main.rollCall` route. Language names in the picker stay as endonyms on purpose.
- The shared app icon is linked as an Avalonia resource. Do not introduce a second product identity without an explicit mobile design decision.
- Android launcher metadata lives in the `SecRandom.Android` head: application ID `cn.sectl.secrandom.mobile`, visible title `SecRandom`, and the shared `AppLogo.png` as its `mipmap/app_logo` resource. Android `versionName` follows the same Git tag as desktop; release CI assigns the GitHub run number as the monotonic Android `versionCode`, so an update APK can replace an earlier build. CI renames the APK to `SecRandom-v<version>-Android-arm64.apk` after signing; a formal release requires all Android keystore secrets so future updates retain the same signer.
- Android checks the shared signed release manifest, verifies APK length/SHA-512, and hands a downloaded update to the system installer through the head's `AndroidUpdateInstaller`. Signed iOS IPAs are included in the shared signed release manifest for release integrity, but iOS device distribution and in-app update delivery remain deferred. The GitInfo version attributes are generated on the head assemblies, so update version detection reads the entry assembly.

## Validation

- Shared library: `dotnet build SecRandom.Mobile.Shared/SecRandom.Mobile.Shared.csproj -c Release`.
- Native UI smoke tests: `dotnet test SecRandom.Mobile.Tests/SecRandom.Mobile.Tests.csproj -c Release`.
- Android: install the `android` workload, Android SDK API 36/build-tools, and JDK 21; then `dotnet build SecRandom.Android/SecRandom.Android.csproj -c Release -p:BuildMobile=true`. When the SDK/JDK are not in the environment, pass `AndroidSdkDirectory` and `JavaSdkDirectory` explicitly.
- iOS: on macOS install the `ios` workload, then `dotnet build SecRandom.iOS/SecRandom.iOS.csproj -c Release -p:BuildMobile=true`. The release signing path requires `IOS_SIGNING_CERTIFICATE_BASE64`, `IOS_SIGNING_CERTIFICATE_PASSWORD`, `IOS_SIGNING_IDENTITY`, and `IOS_PROVISIONING_PROFILE_BASE64`.
