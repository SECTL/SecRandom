# SecRandom.Mobile.Shared/ AGENTS.md

## Scope

This project is the shared Android/iOS Avalonia SingleView shell library. It must not reference the desktop `SecRandom` application project or reuse its `App`, `BuildHost()`, desktop windows, desktop data-path assumptions, or desktop hosted services. The `SecRandom.Android` and `SecRandom.iOS` head projects own the platform entry points and reference this library.

## Project Layout

- This library always builds as neutral `net10.0`. Its `AssemblyName`/`RootNamespace` stay `SecRandom.Mobile` so Core `InternalsVisibleTo("SecRandom.Mobile")` and `avares://SecRandom.Mobile/` resource URIs keep working; C# namespaces stay `SecRandom.Mobile.*`.
- `BuildMobile=true` is consumed only by the `SecRandom.Android` / `SecRandom.iOS` head projects: it switches each head to `net10.0-android` / `net10.0-ios` Exe output. `MobileTargetFramework` no longer exists; build the head project directly for a platform-specific build. The heads set `PlatformStartupContext` with a `MobilePlatformServiceRoot` before `MobileApp` is initialized. CI builds Android packages and continuously compiles the unsigned iOS arm64 target. The unsigned arm64 IPA is a required input to manual release publication and is uploaded with the other release assets. iOS device distribution and in-app update delivery remain deferred.
- Platform seams live behind injectable contracts in this library: `IMobileUpdateInstaller` (with `UnsupportedMobileUpdateInstaller` fallback) abstracts update package staging/installation, and `MobilePlatformServiceRoot.StartupErrorLogger` lets the Android head attach `Android.Util.Log` startup diagnostics. The shared library must not contain `#if ANDROID` / `#if IOS` platform code.
- Telemetry reuses the desktop seam by link-compiling `SecRandom/Services/Telemetry/*.cs` (excluding the desktop-only `TelemetryTransactionSentryExtensions.cs`) with the `Sentry` package; `MobileApp` registers `ITelemetrySdkAdapter`/`TelemetryRuntimeService`, initializes after `host.StartAsync()`, and shuts down before `host.StopAsync()`. Sentry.Profiling is not referenced (its targets error on Android/iOS); the no-op `Services/Telemetry/MobileProfilingIntegrationStub.cs` satisfies the adapter's `AddProfilingIntegration` reference, which the adapter's OS gate never executes on mobile. Unhandled-exception hooks live in the platform heads' `MobileEntryPoint.cs` and report through `IAppHost.TryGetService<TelemetryRuntimeService>()`; upload is gated by `PrivacySettings.SentryTelemetryEnabled`.
- `MobileApp` owns the minimal mobile Host and assigns `MobileRootView` to the SingleView lifetime. `MobileRootView` owns fixed mobile chrome around an inner physical `ViewHostControl`, which is attached through `SingleViewHostProvider`; keep its registrations limited to features actually supported on mobile.
- Before building that Host, `MobileApp` calls `Utils.ConfigureMobileDataRoot()` once to select `LocalApplicationData/SecRandom/data`. The Host then calls `AddCoreRuntimeServices()` to register the host-internal Core JSON config, profile, temporary-record, lottery-availability, and draw services; it assigns `IAppHost.Host` only for transitional Core consumers and clears it during shutdown. Never reuse the desktop package-root `data/` path or add desktop hosted services.
- `MobilePlatformServiceRoot` must explicitly report unsupported desktop window, tray, shortcut, UIAccess, URL registration, and background-residency capabilities.

## UI And Resources

- The fixed bottom bar selects MVE routes: `main.rollCall`, `main.history`, `main.overview`, and `settings.mobile`. The root shell must not directly construct business pages. `MobileDrawPage`, `MobileHistoryPage`, `MobileOverviewPage`, and `MobileSettingsCatalogPage` are logical `ViewBase` sessions. Each mobile settings destination is independently registered under `settings.mobile.*`; the catalog retains exactly `通用`, `个性化`, `名单管理`, `抽取`, `备份`, `更新`, and `关于`, grouped under `偏好` / `数据` / `应用` section headers, with the `更新` entry projected by `MobileCapabilities.SupportsInAppUpdate` (hidden when the platform installer is unsupported).
- Mobile keeps the Fair/Random roll-call mode selector, but Fair must use the fixed `MobileDesktopDefaultsV1` Core policy snapshot and must not expose or consume persisted `FairDrawSettings`. Backup/restore uses Core `DataArchiveService` (already registered by `AddCoreRuntimeServices()` with the Null post-import hooks) behind the system StorageProvider pickers: exports stage a local temp file then copy its stream into the picked `IStorageFile`, imports copy the picked stream to a temp file, run the v3 manifest inspection, and only execute the import after explicit confirmation. All file exchange is stream-only — never assume shared-storage paths under Android SAF — and busy operations disable every action with progress text. Do not add desktop-only settings, tray/window controls, shortcuts, OOBE, audio/notification surfaces, or fake inactive controls.
- `MobileOnlineStatusService` is a mobile-only hosted runtime consumer of `PrivacySettings.OnlineStatusMode`: `Off` makes no network requests; `Anonymous` uses an empty UUID and no IP-derived data; `Full` uses a persisted mobile-private `data/config/device-uuid.json`. Native device types are `android` and `ios`; do not report native mobile clients as web clients.
- Mobile pages live under `Views/`; shared visual construction helpers belong in `MobileUi`/`MobileTheme`; Core services remain the reusable backend boundary.
- Visual tokens live in `Styles/MobileStyles.axaml` (Light/Dark theme color dictionaries, spacing/corner/font/touch-height metrics, and the `MobileCard` ControlTheme), loaded by the compiled `MobileApp.axaml` application resource tree. Avalonia automatically collects local `.axaml` files as `AvaloniaXaml`; do not also declare this file as an `AvaloniaResource`, which would create duplicate resource paths. Pages must consume colors through `MobileTheme.BindBrush`/`MobileTheme.Resource` DynamicResource bindings so theme switches refresh page content; the legacy `MobileTheme.*` snapshot brushes are shell-only (root/header/navigation bar with explicit `RefreshTheme()`) and must not be used by page content.
- Mobile uses `FluentAvaloniaTheme` and FluentAvalonia controls as its primary visual component library so navigation and settings stay aligned with the desktop app. `MobileNavigationBar` hosts a top-mode `FANavigationView` in the fixed bottom shell row, and `MobileSettingRow` wraps `FASettingsExpanderItem`. Avalonia-native controls remain appropriate for the SingleView host, page `ScrollViewer`, and platform touch/layout boundaries. Mobile icon sources must use the mobile assembly font URI rather than Core's desktop `avares://SecRandom/` URI. Reusable mobile controls live in `Controls/`: `MobileCard`, `MobileSettingRow`, `MobileSegmentedControl`, `MobileEmptyState`, and `MobileSectionHeader`; `MobileUi` factory signatures remain the compatibility surface for existing pages.
- Every page-level `ScrollViewer` is created by `MobileUi.CreateScroll`, stretches inside the physical view host, enables vertical inertia, and disables scroll chaining. Clickable setting rows must cancel their click visual/action after pointer movement so they never consume a vertical swipe.
- Animation primitives live in `Views/MobileAnimations.cs`: page enter and result reveal use Android-safe opacity fades (250-400 ms, CircleEaseOut), plus name roll for in-progress draws and state cross-fade. Animations are interruptible per control — starting a new one cancels the old, and visual-tree detach cancels. Animation failures must remain non-fatal because they are decorative. Keep them light; do not port the desktop rolling animation.
- Settings pages should derive from `MobileSettingsPageBase` (light header, back button, scroll, enter transition). Capability projection (`IsLotteryEnabled`, `IsAndroid`, `SupportsInAppUpdate`) is consumed only through `MobileCapabilities` or the base-class pass-throughs, never via raw `OperatingSystem` checks or direct service lookups in pages.
- The shared list/pool name fallback is `MobileDefaults.ProfileName`; do not re-hardcode `"default"`.
- Mobile uses the platform system font by decision recorded in DESIGN.md; do not link the desktop MiSans payloads.
- Mobile strings live in `Langs/Mobile/`; preserve the base resx/designer registration pattern in the project file. `Resources.resx` is the Chinese base; `Resources.en-US.resx` and `Resources.ja-JP.resx` are satellite variants that must keep exact key parity with the base and must not be registered in the csproj. All page/control/service strings resolve through `Langs.Mobile.Resources` (LR); no hardcoded UI strings.
- Startup culture is initialized in `MobileApp.OnFrameworkInitializationCompleted` before the Host is built: `InitializeMobileLanguage()` deserializes `settings.json` directly (desktop-equivalent minimal path) and `ApplyMobileCulture` sets the four thread cultures plus `Langs.Mobile.Resources.Culture`. Language switching is restart-free: the general settings page writes the config, applies the culture, then `MobileApp.ReloadRootViewAsync()` closes/destroys the current root-view host session, detaches it from `SingleViewHostProvider`, swaps in a fresh `MobileRootView` (built via `ActivatorUtilities`, not the DI singleton), and re-shows the default `main.rollCall` route. Language names in the picker stay as endonyms on purpose.
- The shared app icon is linked as an Avalonia resource. Do not introduce a second product identity without an explicit mobile design decision.
- Android launcher metadata lives in the `SecRandom.Android` head: application ID `cn.sectl.secrandom.mobile`, visible title `SecRandom`, and the shared `AppLogo.png` as its `mipmap/app_logo` resource. Android `versionName` follows the same Git tag as desktop; release CI assigns the GitHub run number as the monotonic Android `versionCode`, so an update APK can replace an earlier build. CI renames the APK to `SecRandom-v<version>-Android-arm64.apk` after signing; a formal release requires all Android keystore secrets so future updates retain the same signer.
- Android checks the shared signed release manifest, verifies APK length/SHA-512, and hands a downloaded update to the system installer through the head's `AndroidUpdateInstaller`. Signed iOS IPAs are included in the shared signed release manifest for release integrity, but iOS device distribution and in-app update delivery remain deferred. The GitInfo version attributes are generated on the head assemblies, so update version detection reads the entry assembly.

## Validation

- Shared library: `dotnet build SecRandom.Mobile.Shared/SecRandom.Mobile.Shared.csproj -c Release`.
- Native UI smoke tests: `dotnet test SecRandom.Mobile.Tests/SecRandom.Mobile.Tests.csproj -c Release`.
- Android: install the `android` workload, Android SDK API 36/build-tools, and JDK 21; then `dotnet build SecRandom.Android/SecRandom.Android.csproj -c Release -p:BuildMobile=true`. When the SDK/JDK are not in the environment, pass `AndroidSdkDirectory` and `JavaSdkDirectory` explicitly.
- iOS: on macOS install the `ios` workload, then `dotnet build SecRandom.iOS/SecRandom.iOS.csproj -c Release -p:BuildMobile=true`. The release signing path requires `IOS_SIGNING_CERTIFICATE_BASE64`, `IOS_SIGNING_CERTIFICATE_PASSWORD`, `IOS_SIGNING_IDENTITY`, and `IOS_PROVISIONING_PROFILE_BASE64`.
